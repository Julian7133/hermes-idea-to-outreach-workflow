# 00b — Träumer

## Kern in einem Satz
Software hört auf, ein Kompromiss für alle zu sein, und wird für den einzelnen
Menschen genau richtig — ohne dass er dafür programmieren oder warten muss.

## Die beste denkbare Version
Ein Nutzer tippt in ein Chatfeld: "Ich will, dass der Speichern-Button links
ist, nicht rechts — ich vertippe mich ständig." Er bekommt keine Ticket-Nummer,
keine "danke für dein Feedback, wir prüfen das" — sondern eine Rückfrage, die
zeigt, dass jemand (oder etwas) wirklich zugehört hat: "Verstanden — soll das
nur für den Speichern-Button gelten, oder für alle primären Aktionen in der
App?" Er bestätigt. Zwei Minuten später ist die App für ihn, und nur für ihn,
anders. Kein Umweg über ein Einstellungsmenü mit hundert Reglern, die eh keiner
findet — die App *wird*, was er gesagt hat. Das Erlebnis ist: zum ersten Mal
fühlt sich Software an wie ein Mitarbeiter, der zuhört und handelt, nicht wie
ein Produkt, das er sich anpassen muss.

## Wer wäre begeistert
Die Betriebsleiterin einer 12-Personen-Werkstatt, die ein Auftragsverwaltungs-
Tool nutzt, das für Konzerne mit Rabattstufen, Filialketten und zehn
Genehmigungsebenen gebaut wurde — für sie ist 90 % davon Ballast, der sie beim
täglichen Erfassen bremst. Sie hat keine IT-Abteilung, die "customized",
sondern nur die Wahl zwischen "damit leben" oder "zurück zu Excel". Wenn sie
einfach sagen könnte, was sie stört, und es würde für sie verschwinden oder
sich ändern — das wäre der Moment, in dem das Tool endlich *ihres* wird statt
irgendeines Standardprodukts, das sie mieten.

## Drei Ausprägungen

### A — Werkzeug
Eine Plattform/ein SDK, das bestehende SaaS-Anbieter einbauen: ein
Chat-Widget plus Agent-Pipeline, die Nutzerwünsche gegen ein definiertes
Regelwerk (Produktvision, technische Grenzen) prüft, vorschlägt, und bei
Bestätigung automatisch ein Feature-Flag pro Nutzer setzt und den Code dafür
generiert. Für: Produktteams kleiner SaaS-Tools, die echte 1:1-Personalisierung
anbieten wollen, ohne eine eigene Config-Engine zu bauen.

### B — Dienstleistung
Julian selbst betreibt das für ein einziges bestehendes internes Tool oder
eine kleine SaaS: Nutzer schreiben Wünsche, ein Agent-Team (mit Julian als
letzter Prüfinstanz) baut die individuellen Anpassungen und liefert sie aus.
Für: Betreiber kleiner interner Business-Tools (z. B. Handwerksbetriebe,
Kanzleien), die spüren, dass ihre Software von der Stange nicht zu ihrem
Arbeitsablauf passt, aber kein Entwicklerteam haben, das sie fragen können.

### C — Nische
Eine radikal zugespitzte Version für eine einzige Werkzeugkategorie mit
extrem heterogenen Nutzern und niedriger Änderungsschwelle: interne Dashboards
für Solo- und Kleinstunternehmer (z. B. Freelancer-Buchhaltungs- oder
CRM-Tools), bei denen "meine Ansicht passt nicht zu meinem Workflow" der
häufigste Absprunggrund ist. Für: Freelancer und Kleinstteams, die ein
generisches Tool nutzen, aber eine ganz eigene Reihenfolge, Feldbezeichnung
oder Ansicht brauchen, um es täglich wirklich zu benutzen statt es nach zwei
Wochen aufzugeben.

## Das wird groß, wenn
1. Der Prüf- und Build-Schritt für einen individuellen Wunsch durch Agenten so
   weit automatisierbar wird, dass er Minuten statt Stunden kostet — sonst
   bleibt es ein Custom-Dev-Geschäft mit Personalisierungs-Anstrich.
2. Es eine Gruppe von Nutzern gibt, deren Frust mit "generischer Standard-
   Software, die nicht zu ihrem Alltag passt" groß genug ist, dass sie aktiv
   danach fragen — nicht nur passiv Feedback-Formulare ignorieren.
3. Sich eine harte, kommunizierbare Grenze ziehen lässt, was änderbar ist
   (Look, Reihenfolge, Feldnamen, Regeln) und was nicht (Kernlogik,
   Datenmodell) — sonst wird jeder Wunsch zum Sonderprojekt.
